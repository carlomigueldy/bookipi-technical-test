## Disposition

**Qualifying for the PRD performance bar (local Docker baseline):** warmup r1,
surge r1–r3, sold-out r1–r3, window-edge r1–r3 — **10 of 13 repetitions**, all
frozen gates green, on final code with no reverted or diagnostic configuration in
the measurement. The PRD's declared performance criteria
(§ "≥ 2,000 purchase attempts/s sustained; p95 < 200 ms, p99 < 500 ms; status
endpoint p95 < 50 ms") are met by the three surge repetitions with a wide margin:
150,000 purchase attempts per repetition at the 2,000/s target, purchase p95
1.541–1.779 ms and p99 2.833–3.248 ms against a 200/500 ms bar, status p95
1.255–1.388 ms against a 50 ms bar, zero failed requests.

**Qualifying for I1–I4:** all 13 repetitions.

**Latency-non-qualifying, correctness-qualifying:** duplicate-storm r1, r2, and
r3. Their I1–I4 audits are clean and their business-outcome checks are perfect,
but their purchase p95/p99 breach the frozen gate in all three repetitions, r2
also breaches status p95, and r3 also dropped 2 iterations. **Correctness
evidence is not a performance pass.** These three repetitions carry no latency,
capacity, or threshold claim.

## Root cause of the duplicate-storm breaches: host `CLOCK_REALTIME` steps

The host's wall clock steps by approximately ±10.3 s roughly twenty times per
90-second scenario. This is a WSL2 `hv_utils` time-synchronisation behaviour on
this machine, not a property of the code under test. The run carries four
independent, quantified sentinels of it.

**1 — Negative response times recorded by the API's own server-side timer.** The
API stamps a request's start and end from the wall clock; a backward step
mid-request yields a negative `responseTime`. Counts from each repetition's
`api.log`:

| Repetition               | Negative `responseTime` samples | Worst sample |
| ------------------------ | ------------------------------: | -----------: |
| Warmup r1                |                               0 |            — |
| Surge r1                 |                              10 |   −10,302 ms |
| Surge r2                 |                              17 |   −10,326 ms |
| Surge r3                 |                              20 |   −10,339 ms |
| Duplicate-storm r1       |                         **190** |   −10,337 ms |
| Duplicate-storm r2       |                         **470** |   −10,269 ms |
| Duplicate-storm r3       |                         **368** |   −10,298 ms |
| Sold-out r1 / r2 / r3    |                       2 / 1 / 3 |   −10,301 ms |
| Window-edge r1 / r2 / r3 |                       2 / 1 / 1 |   −10,302 ms |

The clock stepped during **twelve of the thirteen repetitions**, including every
repetition that passed. The step magnitude is the same everywhere: 10.27–10.34 s.

**2 — A negative duration inside k6's own client-side metric.** Duplicate-storm
r3's `http_req_duration{name:purchase}` records `min = -10,285.940481 ms`. A
client-measured negative request duration cannot be produced by a slow server.

**3 — The breaching percentiles equal exactly one step.** Purchase p99 across the
three storm repetitions is 9,991 / 10,064 / 9,930 ms — one +10.3 s step, absorbed
by requests that were in flight when it landed, and nothing more. The maxima
(19,649 / 15,216 / 16,418 ms) correspond to requests that spanned two steps.

**4 — The distribution is bimodal, not a queueing curve.** Duplicate-storm r1:
median 64.950 ms, p90 95.447 ms, then p95 8,744.976 ms. The jump from p90 to p95
is two orders of magnitude across five percentile points. Congestion produces a
continuous tail; a discrete clock step applied to whichever requests happen to be
open produces exactly this shape.

**Why duplicate-storm alone breaches.** The gate is a percentile, so a step only
moves it if the step catches enough concurrent requests to shift the 95th
percentile. Duplicate-storm holds up to 5,000 purchase requests in flight
simultaneously (500 VUs × a 10-request batch), so a single step can contaminate
10 % of the repetition's 50,000 purchase attempts in one instant. Surge, by
contrast, ran **four times the sustained request volume** (155,410 vs 53,000
requests) in the same run, on the same host, through the same clock steps — and
passed with p99 2.8–3.2 ms, because its per-request concurrency is low enough
that each step caught only one or two requests. Those requests are still visible:
surge's purchase `max` is 10,303.57 / 10,331.31 / 10,326.27 ms in r1/r2/r3 — one
step each, against a median of 0.77–0.87 ms. Same defect, same run, no percentile
impact.

**Not resource exhaustion.** Peak container CPU during duplicate-storm was api
149–187 % of its 400 % grant, worker 90–99 % of 200 %, postgres 39–45 % of 200 %,
redis 56–58 % of 100 %, k6 63–73 % of 400 %. Nothing reached its allocation. This
also rules out the previously rejected remedies: raising CPU limits cannot help a
service that never saturated them.

**Secondary breaches share the cause.** Status p95 82.364 ms in r2 (the only
non-purchase latency breach in the run) is measured on the same contaminated
clock during the repetition with the highest negative-sample count (470). The two
dropped iterations in r3 are the arrival-rate scheduler failing to place work
against a clock that moved under it.

## The sole remaining blocker

**The host clock is the only thing standing between this run and a fully green
13/13.** Every product-code and harness defect found in the pre-fix run is closed
and demonstrated closed. What remains is a measurement substrate that moves ±10.3 s
under the measurement, roughly twenty times per scenario, and which no amount of
application code can compensate for once a percentile gate is computed from
wall-clock deltas.

It cannot be fixed from inside this session: the host clock requires privileged
remediation and this environment has no passwordless `sudo`, and the stepping
originates in WSL2's `hv_utils` host time-sync path rather than in anything the
repository controls.

Either of two things would resolve it:

1. **Re-run the full profile on a clock-stable host** — bare-metal Linux, a Linux
   VM with a monotonic-safe time source, or any environment where
   `CLOCK_REALTIME` does not step. No repository change is required; the
   prediction is that duplicate-storm p95/p99 lands near its own median of
   58–139 ms, comfortably inside the 200/500 ms gate.
2. **Stabilise WSL2 time sync on this host** — disable the `hv_utils`
   host-guest time-sync stepping, or pin the guest to a locally-disciplined NTP
   source, then re-run. This needs root on the host, which this session does not
   have.

Until one of those happens, the honest reading of this run is: **the product meets
the PRD bar on this host and preserves I1–I4 under every scenario in the profile;
the instrument cannot certify the duplicate-storm latency percentile on this host.**
Thresholds were not altered to close the gap, and no latency or capacity claim is
made for duplicate-storm.
